## 무엇이 잘못되어 있었나

삽입은 **query(read)를 소비하고 reference는 소비하지 않습니다.** 결실은 그 반대입니다.
기존 코드는 이 비대칭을 세 곳에서 놓치고 있었습니다.

### 1. LIS 체인에서 삽입 구간을 덮어썼다 (`align.cpp`, 주 원인)

두 seed 블록 사이에 query 좌표 간격이 생기면 그것이 곧 삽입 서열입니다.
기존 코드는 다음 블록을 그 위로 끌어당겼습니다:

```c
int gap = lis_res[i].st2-lis_res[i-1].ed2-1;
if(gap>K+K/2){ lis_res.clear(); return; }   /* 체인 자체를 폐기 */
lis_res[i].st2-=gap;                        /* 삽입 염기 위로 밀어버림 */
```

밀어버린 결과 삽입 염기 하나하나가 전부 mismatch가 되고, 곧이어 `miss>=8` 가드가
정렬 전체를 버립니다. 간격이 `K+K/2`(K=11이면 16 bp)를 넘으면 아예 체인을 비웁니다.
**결실은 query 간격이 0이라 두 가드에 걸리지 않습니다.** 삽입만 사라진 이유입니다.

계측 결과 PRR5의 junction 보유 pair 41,548개 중 **13,919개(33.5%)가 `miss>=8`에서,
13,031개(31.4%)가 체인 폐기로** 탈락하고 있었습니다.

### 2. `make_cigar()` 가 삽입을 CIGAR에 적지 않았다

reference 좌표가 겹칠 때만 `I`를 만들고, query 간격은 표현하지 않았습니다.
그래서 16 bp를 넘는 삽입은 CIGAR에 크기 정보가 전혀 없었고 전부
"terminal insertion" 한 버킷으로 들어갔습니다.

### 3. `read_classify()` 가 `I`에서 reference 커서를 뒤로 돌렸다

```c
case 'I':
    ...
    pos-=now.len;   /* I는 reference를 소비하지 않는데 뒤로 감 */
```

1–3 bp에서는 무해했지만 `I`가 길어지면 `ref_ed`가 크게 틀어집니다.

## 무엇을 고쳤나

`align.cpp` 6곳, 전부 `arg.ins_fix`로 감싸 두었습니다 (0이면 기존 동작 그대로).

| # | 위치 | 내용 |
|---|---|---|
| 1 | `read_classify()` `case 'I'` | reference 커서를 되돌리지 않음 |
| 2 | `make_cigar()` | query 간격을 `I`로 기록. reference 겹침과 **합산**해 하나의 `I`로 — 인접한 `I` 두 개는 적법한 CIGAR가 아니고 htslib가 거부함 |
| 3 | `make_cigar()` 커버리지 하한 | `r_match < 0.8*query_len` → `0.8*(query_len-ins_total)`. 삽입 염기는 reference가 맞출 수 없으므로 하한에서 제외 |
| 4 | 좌측 walk-back | `qfloor` 도입 — 이전 블록 끝을 넘어 삽입 염기를 잠식하지 않음 |
| 5 | 우측 walk-back | `qceil` 도입 — 동일 |
| 6 | `gap>K+K/2` 가드 | query 간격이 reference 간격보다 크면(= 삽입) 두 커서를 그대로 두고 통과. `ins_max`를 넘으면 폐기 |

4·5번은 부수 효과가 컸습니다. walk-back 경계를 잡아주자 **체인 폐기가 64%,
`prune_short_ends` 탈락이 33% 줄었습니다.**

## 검증

### 시뮬레이션 (TRAC / HPRT1 / BCL11A, 20만+ 분류 pair)

크기별 전후는 `insertion_fix_improvement.tsv`에 전부 들어 있습니다. 요지:

- 삽입 9–20 bp: **46.0% → 96.8%**
- 삽입 크기를 CIGAR의 `I` 길이로 처음 보고 — 1–100 bp 전 구간에서
  정답과 **정확히 일치 96–98%**, ±1 bp 이내 99%
- 결실·WT·오분류율은 소수점 첫째 자리까지 동일

### junction homology 스트레스셋

PRR5의 삽입은 무작위가 아니라 **앞 11 bp가 cut 하류 26 bp 지점의 reference와 정확히
일치**합니다. 이것이 한계 요인인지 확인하려고 같은 모양의 세트를 만들어 재봤습니다
(삽입 길이 L, 앞 H bp가 하류 26 bp와 동일):

| L | H | 정답률 전 → 후 |
|---|---|---|
| 20 | 0 | 38.8% → 96.9% |
| 20 | 8 | 41.3% → 99.2% |
| **20** | **11** | 41.2% → **99.0%** ← PRR5와 동일 조건 |
| 20 | 16 | 33.0% → 90.3% |
| 20 | 20 | 33.3% → 83.4% |
| 26 | 26 | 24.6% → 66.6% |

**homology는 PRR5의 한계 요인이 아닙니다.** 삽입의 대부분이 reference 유래일 때
(H≥16)부터 비용이 생기고, PRR5는 안전 구간 안쪽입니다.

### PRR5 잔여 손실의 정체

계측 빌드로 junction 보유 pair 41,548개의 탈락 지점을 세었습니다:

| 탈락 지점 | 수정 전 | 수정 후 |
|---|---|---|
| `miss >= 8` 가드 | 13,919 (33.5%) | **63 (0.2%)** |
| seed 체인 폐기 | 13,031 (31.4%) | 4,718 (11.4%) |
| `prune_short_ends` | 5,530 (13.3%) | 3,728 (9.0%) |
| anchor 품질 < 13 | 2,400 (5.8%) | 2,930 (7.1%) |
| 첫 `chunk_align` | 1,129 (2.7%) | 526 (1.3%) |
| **합계** | **36,067 (86.8%)** | **12,204 (29.4%)** |

read 안에서 junction 위치별로 나눠 보면 남은 손실은 알고리즘이 아니라 **기하학**입니다:

| junction 시작 위치 | 0–14 | 15–29 | 30–44 | 45–59 | 60–74 | 75–89 | 90–104 | 105–119 | 120+ |
|---|---|---|---|---|---|---|---|---|---|
| 수정 전 | 11% | 0% | 0% | 0% | 0% | 0% | 0% | 0% | 37% |
| **수정 후** | 27% | **78%** | **85%** | **90%** | **92%** | **90%** | **81%** | **79%** | **79%** |

read 가운데는 78–92%로 회복됩니다. 첫 구간만 27%에 머무는데, junction이 read 시작에서
15 bp 안쪽이면 그쪽 flank에 앵커를 잡을 reference가 없고 anchor 필터가 남은 것을
정당하게 거부하기 때문입니다. **150 bp read의 정보 한계지 고칠 수 있는 결함이 아닙니다.**

### 대형 결실 판정에 미치는 영향

분류 대상 pair가 늘면 k-means 군집 경계가 움직일 수 있어 따로 확인했습니다.

**결실 2 kb 미만: 세 레퍼런스 전부 변화 없음** (0.2 pp 이내).

| 결실 길이 | TRAC only 전→후 | HPRT1 only 전→후 | BCL11A only 전→후 |
|---|---|---|---|
| 50–99 | 28.6 → 28.7 | 21.0 → 21.1 | 20.1 → 20.1 |
| 100–249 | 28.9 → 29.0 | 21.2 → 21.2 | 20.3 → 20.3 |
| 250–499 | 30.0 → 30.0 | 21.7 → 21.8 | 20.6 → 20.6 |
| 500–999 | 38.0 → 38.1 | 27.4 → 27.3 | 26.3 → 26.3 |
| 1000–1999 | 40.5 → 40.5 | 28.8 → 28.8 | 27.4 → 27.4 |
| 2000–4000 | 47.4 → 47.4 | 31.7 → 26.9 | 30.4 → 30.5 |
| 4001–9000 | 72.8 → 72.8 | 15.3 → 39.9 | 42.2 → 40.1 |

**결실 2 kb 이상에서는 only/common 분할이 움직입니다.** 다만 이것은 이 수정의
효과가 아니라 **군집 단계가 원래 입력에 불안정하기 때문**입니다. 입력의 1%만
무작위로 덜어내도(수정 없이) 같은 크기로 흔들립니다:

| HPRT1 | 2–4 kb only | 4–9 kb only | 전체 호출 (4–9 kb) | 사용된 군집 수 |
|---|---|---|---|---|
| 전체, 수정 전 | 31.7% | 15.3% | 53.9% | 27 |
| 전체, 수정 후 | 26.9% | 39.9% | 53.0% | 24 |
| 99% 표본 A, **수정 없음** | 31.8% | 42.2% | 54.0% | 30 |
| 99% 표본 B, **수정 없음** | 26.8% | 37.8% | 53.9% | 27 |
| 99% 표본 C, **수정 없음** | 31.8% | 45.9% | 53.9% | 30 |

수정 없이 표본만 바꿔도 4–9 kb의 only 비율이 37.8–45.9%로 8.1 pp 퍼집니다.
수정 후 값 39.9%는 그 한가운데이고, **오히려 수정 전 15.3%가 이상치**입니다.
2–4 kb도 마찬가지로 표본 B가 26.8%로 수정 후 26.9%와 사실상 같습니다.

자세한 내용은 `LARGEDEL_CLUSTER_INSTABILITY.md` 를 보십시오.

**탐지 자체는 흔들리지 않습니다.** 전체 호출(only+common)은 다섯 실행 전부
2–4 kb 32.0–32.5%, 4–9 kb 53.0–54.0% 로 안정적이고, 특이도도 유지됩니다:

```
WT -> only 위양성      0.04% ~ 0.11%  (다섯 실행 전부)
키메라 -> only 오보고  16.7% ~ 19.8%  (다섯 실행 전부)
TRAC_large   WT->LDEL_ONLY 0.00% -> 0.00%   키메라->only 30.2% -> 30.2%
BCL11A_large WT->LDEL_ONLY 0.00% -> 0.00%   키메라->only 25.0% -> 24.4%
대형 결실 호출 수 (TRAC_large)  34,786 -> 34,837
```

## 사용법

기본값이 켜짐이므로 **기존 명령줄을 그대로 쓰면 수정이 적용됩니다.**

```bash
# 기존과 동일 — ins_fix=1 이 기본
./kmer_align ref.fa ctr_1.fq ctr_2.fq mut_1.fq mut_2.fq 4652 4671 3 HPRT1 TEST 11 outdir

# 수정 전 동작으로 되돌리기 (인자 13~18을 모두 채워야 19번에 닿습니다)
./kmer_align ref.fa ctr_1.fq ctr_2.fq mut_1.fq mut_2.fq 4652 4671 3 HPRT1 TEST 11 outdir \
             1000 1 bam 400 13 1 0

# 60 bp를 넘는 삽입은 정렬하지 않음
./kmer_align ... 1000 1 bam 400 13 1 1 60
```

`./kmer_align --help` 에 두 인자 설명이 들어 있습니다.

## 입력 처리도 함께 고쳤습니다 (2026-09-22 추가)

삽입 수정을 실제 데이터에 돌리면서 걸린 두 가지를 같이 고쳤습니다.
분류 로직과 무관하고, 같은 입력에 대해 결과는 완전히 동일합니다.

| 파일 | 내용 |
|---|---|
| `func.cpp` `ka_open()` (신규) | `.fastq.gz` / `.bz2` / `.xz` 를 그대로 읽습니다. 해당 압축 해제기로 파이프를 열어 넘기므로 나머지 코드는 손대지 않았습니다. 압축 해제가 별도 프로세스에서 돌아 **오히려 더 빠릅니다** (61만 pair 기준 21.3초 → 17.7초). |
| `func.cpp` `make_ref()` | 줄바꿈된 FASTA 를 받습니다. 기존에는 `fscanf("%s")` 두 번으로 읽어서 **60자로 접힌 FASTA 를 주면 첫 60 bp 만 레퍼런스가 되고 정렬률 0% 가 나왔습니다 — 에러 메시지도 없이.** 이제 헤더 뒤의 모든 서열 줄을 이어 붙이고 소문자를 정규화하며, 읽은 길이를 `[ref] 파일명: N bp` 로 찍습니다. |
| `align_wrap.cpp` | FASTQ 도 `ka_open()` 으로 열고 `ka_close()` 로 닫습니다. |

```bash
# 이제 이렇게 바로 됩니다
./kmer_align ref.fa ctr_1.fastq.gz ctr_2.fastq.gz mut_1.fastq.gz mut_2.fastq.gz \
             4682 4701 17 PD1 sg1 11 outdir 8000 0 sam 400 13 1 1
```

검증: 같은 데이터를 (평문 FASTQ + 한 줄 FASTA) 와 (gz FASTQ + 60자 줄바꿈 + 대소문자
혼합 FASTA) 로 각각 돌려 `mutation_summary.tsv` 가 완전히 동일함을 확인했습니다.

## HTML 리포트 — `kmer_align` 에 내장 (2026-09-23)

처음에는 Python 스크립트(`ka_report.py`)로 만들었다가 **C++ 로 옮겼습니다.**
이제 `kmer_align` 을 한 번 돌리면 결과 폴더에 리포트가 같이 생깁니다.

```
<outdir>/<gene>_<sample>_report.html   이 실행 하나의 리포트 (자기완결, CDN 없음)
<outdir>/<gene>_<sample>_report.tsv    여러 실행을 합칠 때 쓰는 집계
```

여러 샘플을 하나로 합치거나 수정 전후를 비교할 때는 같은 바이너리의 하위명령:

```bash
./kmer_align report -o PD1.html --compare result/*_OFF -- result/*_ON
```

### 왜 C++ 로 옮겼나

| | Python | C++ 내장 |
|---|---|---|
| 데이터 출처 | 방금 쓴 SAM 을 **다시 파싱** | SAM 레코드가 쓰이는 순간 `samout_write()` 에서 집계 |
| 원본 FASTQ 대조 (247만 read) | 약 45초 | **5.2초** |
| 실행 방법 | 별도 명령 + Python 필요 | `kmer_align` 한 번 |
| 웹 도구 (WASM) | 불가 | **그대로 따라감** |

분류 코드는 한 줄도 건드리지 않았습니다. 집계는 `samout_write()` — 모든 출력
레코드가 지나가는 한 곳 — 에서만 하므로 리포트와 SAM 파일이 어긋날 수 없습니다.

### 구성

| 파일 | 내용 |
|---|---|
| `report.h` / `report.cpp` (신규) | 집계, 원본 FASTQ 대조, `.tsv` 입출력, `kmer_align report` 하위명령 |
| `report_tpl.h` (신규) | HTML 템플릿 — CSS 와 JS 를 raw string 으로. JS 가 데이터 객체 하나로 페이지 전체를 그려서 **단일 실행 리포트와 합친 리포트가 같은 템플릿**을 씁니다 |
| `samout.cpp` | 출력 파일마다 역할 태그를 달고 `samout_write()` 에서 `report_observe()` 호출 |
| `align_wrap.cpp` | 요약표를 쓴 직후 `report_finish()` 호출 |
| `kmer_align.cpp` | 첫 인자가 `report` 면 합치기 모드 |
| `arg_parse.*` | 인자 **#21 `report`** (기본 1, 0 이면 리포트와 FASTQ 재스캔 생략) |
| `func.cpp` | `__EMSCRIPTEN__` 에서는 `popen` 을 쓰지 않도록 가드 (브라우저엔 프로세스가 없음) |
| `web/build.sh` | 소스 목록에 `../report.cpp` 추가 |

### 리포트 내용

- 요약 타일 — 정렬 pair, 분류 대상, 편집 비율, 최대 삽입 길이, 8 bp 이상 삽입 수
- **인델 크기 스펙트럼** — 결실(−)/삽입(+) 양방향, ±30/±10/전체, y축 로그 전환
- 분류 구성 누적 막대 + 표
- **대형 결실 크기 분포** (처리군 vs 대조군), 2 kb 이상 구간 재현성 경고
- **8 bp 이상 삽입 서열 표** — 후보 서열을 처리군·대조군 **원본 FASTQ 에서 직접 세어**
  백만 read 당 빈도로 비교. 대조군이 처리군의 절반 이상이면 "아티팩트", 원본에서
  5번 미만이면 "근거 부족" 으로 단정하지 않습니다
- `--compare` 시 **수정 전후** — 삽입 길이 구간 막대(로그) + 분류 비율 전→후 표

### 검증

- PD1 sg1_1: `mutation_summary.tsv` 와 SAM 8종(site 4, only/common 4) 이
  리포트 추가 전과 **바이트 단위로 동일**

## 빌드 주의

**Makefile 의존성을 고쳤습니다.** 기존 오브젝트별 의존성 목록에 빠진 헤더가 있었습니다
(`align.o`, `post.o` 가 `arg_parse.h` 를 안 적음). 그래서 `struct Args` 에 필드를 추가하면
두 오브젝트가 재컴파일되지 않았고, `post_process()` 가 `Args` 를 **값으로** 받기 때문에
구조체 크기가 어긋나 실행 중 힙이 깨졌습니다 (`free(): invalid size`). 이제 모든 오브젝트가
모든 헤더와 `Makefile` 자체에 의존하므로, 새 Makefile 로 `make` 하면 전부 다시 빌드됩니다.

> **Makefile 은 직접 적용하셔야 합니다.** 원격 도구로는 Makefile 을 쓸 수 없게 보호돼
> 있어서 저장소에는 반영하지 못했습니다. 새 Makefile 과 `Makefile.report.patch` 를 따로
> 드렸습니다 — 이게 없으면 `report.cpp` 가 오브젝트 목록에 없어 **링크 에러**가 납니다.
> ```bash
> patch Makefile < Makefile.report.patch    # 또는 새 Makefile 로 교체
> make
> ```


저장소에 있던 `.o` 파일들이 현재 환경과 다른 glibc로 빌드되어 있어
(`__isoc23_fscanf` 미해결) 증분 빌드가 링크에서 실패합니다. 전체 재빌드가 필요합니다:

```bash
touch *.cpp && make
```

`make clean` 은 `.hts_probe.cc` 삭제에서 막힐 수 있으니 위 방법을 권합니다.
